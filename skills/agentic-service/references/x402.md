# x402 implementation notes

Use official sources and the installed package source/types for the version in use:

- Protocol and reference SDK: https://github.com/x402-foundation/x402
- Cloud discovery: https://docs.cdp.coinbase.com/api-reference/v2/rest-api/x402-facilitator/list-x402-resources
- Named CDP accounts: https://docs.cdp.coinbase.com/server-wallets/v2/using-the-wallet-api/managing-accounts

## Verified Express integration

The initial diagram service used x402 packages 2.28.0. These imports and conventions were exercised:

```js
import { paymentMiddleware, x402ResourceServer } from '@x402/express';
import { HTTPFacilitatorClient } from '@x402/core/server';
import { ExactEvmScheme } from '@x402/evm/exact/server';
import {
  bazaarResourceServerExtension,
  declareDiscoveryExtension,
} from '@x402/extensions/bazaar';

const server = new x402ResourceServer(facilitator)
  .register(network, new ExactEvmScheme())
  .registerExtension(bazaarResourceServerExtension);

// Validate the body before this middleware. Attach the actual handler after it.
app.use(paymentMiddleware({
  'POST /v1/work': {
    accepts: [{ scheme: 'exact', network, payTo, price: '$0.01' }],
    description: 'Describe the concrete result the caller receives',
    mimeType: 'application/json',
    extensions: declareDiscoveryExtension({
      method: 'POST', bodyType: 'json', input: example, inputSchema,
    }),
  },
}, server));
```

`declareDiscoveryExtension` already returns `{bazaar: ...}`; do not wrap it again. For Zod-generated request schemas, use `io: 'input'` so defaulted fields remain optional. Validate the declared example against that schema. Bazaar's `output.example` expects an object; omit it for raw HTML/SVG responses rather than declaring a misleading JSON wrapper.

The middleware's facilitator initialization is enabled by default. Passing `false` as `syncFacilitatorOnStart` without separately initializing the resource server produced unsupported-payment-kind errors.

Headers in x402 v2:

- Unpaid response: 402 + `PAYMENT-REQUIRED` (base64 JSON).
- Paid retry request: `PAYMENT-SIGNATURE` (base64 JSON).
- Settled response: `PAYMENT-RESPONSE` (base64 JSON).

The Express SDK buffers the handler response and releases it after settlement. Test both rejected verification and failed settlement; neither should return the protected artifact.

## Networks and credentials

Base Sepolia: `eip155:84532`; Base mainnet: `eip155:8453`. Network names are CAIP-2 identifiers in the x402 API. Token contract and decimals must come from the chosen network's current documented SDK configuration.

The public `https://x402.org/facilitator` was exercised for Base Sepolia. Do not assume it supports production settlement. For a hosted production facilitator, configure that provider's supported authentication. CDP API credentials for a facilitator do not require deploying a wallet secret; prefer credentials scoped to the service where the provider supports that.

For a named CDP seller account, `getOrCreateAccount({name})` is idempotent. Reusing a name preserves the account; changing the name can create a fresh account. `updateAccount` can rename an existing account without changing its address. Wallet setup should not inadvertently fund, transfer, or export keys.

For an actual test purchase, use a separate named buyer, test USDC faucet, and the official client's exact scheme. Check the offered recipient, network, and amount before signing. A faucet receipt can precede facilitator balance visibility; if verification rejects an initially funded buyer, inspect the rejection and retry with the same intended test terms after confirming visibility. Avoid printing payment proofs or credential-bearing error objects.

The CDP x402 module used an optional `@x402/svm` dependency even in an EVM-only import path. Check peer dependencies when importing that module. A narrower adapter can avoid unnecessary transport dependencies, but must be verified against the installed SDK.
